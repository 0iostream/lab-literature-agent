## 已从代码与计划沉淀的教训

1. **「不确定」误判拒答**  
   拒答检测曾可能把讨论性措辞当成拒答。应用明确拒答标记列表（如「我不知道」「证据不足」），避免过宽匹配。

2. **同一秒多次 run 共用 trace 文件**  
   Trace id 需「时间戳 + 短 uuid」，避免覆盖或串写。

3. **NO_HITS 后仍硬答**  
   无检索命中时应 `rewrite_query` 再搜或拒答；禁止编造 `[doc#chunk]`。引用必须通过 `DocumentStore.get` 校验。

4. **一上来就 rewrite**  
   浪费步数且易漂题；规则是先 `search_docs`，仅 NO_HITS 再改写，并保留专有名词与数字。

5. **闲聊/算术误触发检索**  
   工具描述与评测都约束：算术走 `python_calc`，寒暄直接答。端到端用 `should_search` / `expect_tools` 卡住回归。

6. **词法与向量分数不能直接相加**  
   混合检索用 RRF 融合候选，而不是对原始 score 蛮力加权。

7. **简历数字无分母**  
   未跑金标就写「准确率很高」无效；数字必须带题数、模型、语料与配置，来自 `last_report.json` 等产物。

8. **Windows 系统 Python**  
   激活脚本失败时仍强行用全局解释器会导致依赖错乱；固定 venv 的 `python.exe -m`。

9. **Demo/评测记忆串话**  
   每题独立 `ConversationMemory`，否则上一题上下文污染工具选择。

10. **可选栈提前写进简历**  
    FastAPI / LangGraph / MCP 未落地就写「熟悉」会面试翻车；RESUME 模板已禁止。
