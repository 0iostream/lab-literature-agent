# Agent 评测与安全边界（学习笔记）

## 评测要拆开算

不要用一个「准确率」概括 Agent。至少分开报告：

- 检索：Recall@k、MRR（查询与相关 chunk 的金标）。
- 工具选择：该搜则搜、不该搜则不搜；算术应走计算器；闲聊不应误触发检索。
- 答案层：可答题的合法引用率；应拒答样本上的 Precision / Recall / F1。
- 成本：平均步数、延迟、token（估算要标明）。

金标题不要放进系统提示，否则指标虚高。

## 拒答与门禁

语料中没有的事实（例如实验室打印机电话、虚构论文、内部薪资）应在检索后明确拒答。引用门禁检查答案中的 [doc_id#数字] 是否能在文献库查到；查不到则触发有限重试或拒答，禁止编造。

## 安全与只读工具

文献问答场景应保持工具只读：检索、精读、改写、算术，不提供删库、发信、付款等副作用接口。用户输入可做简单黑名单拦截；检索文档内容视为数据，不能覆盖系统规则（防范文档内嵌的提示注入）。

## Bad case 怎么用

把可复现失败记成案例：拒答规则误伤、答案外推超出片段、拒答却堆无关引用等。每个案例写清输入、期望、实际与根因。回归时优先跑这些题，而不是只看平均分涨跌。

## HTTP 服务边界

把 Agent 收成接口时，健康检查应轻量、不跑完整循环；问答接口要做输入长度校验、整题超时、统一错误码，并且每请求独立会话记忆，避免评测或用户之间串话。

## 混淆矩阵与拒答 F1

把「应拒答」当正类：真正拒答为 TP，不该拒却拒了为 FP，该拒却答了为 FN。Precision = TP/(TP+FP)，Recall = TP/(TP+FN)，F1 为二者调和平均。只看准确率会掩盖「几乎从不拒答」的系统在拒答任务上的失败。

## 回归策略

每次改系统提示、检索模式或门禁规则后，至少重跑：检索金标子集、端到端金标、以及 notes 里记录的 bad case。若指标上升但 bad case 复发，不能算改进。报告应保存模型名、题数、配置与时间，方便简历与面试引用同一份文件。

## 成本意识

Agent 成本主要来自多轮把历史 messages 反复送给模型。固定前缀缓存能降低重复系统提示的费用，但不能代替裁剪 Observation。对比实验里把平均步数和延迟写进报告，比只写「用了某某框架」更有说服力。

## 固定 RAG 对照

除 Agentic 外，保留一条「先搜再答」的固定基线，能说明 Agent 多出来的步数换到了什么：更少误检索、更好拒答，或只是更慢。对照必须同题、同库、同模型，否则结论无效。

## 人工抽查样本量

忠实度抽查不必每题都做，但应覆盖成功与失败案例，并写下「支持 / 部分支持 / 不支持」。把「部分支持」单独统计，避免把轻微外推和完全编造混为一谈。


## 补充：实践中的取舍

实习项目的文献库贵在「可复现、可评测、能讲清方法」，不在于堆到百万字。把同一套切分、检索、引用与拒答流程跑通，并保存带配置的评测报告，比盲目扩库更有说服力。扩库时优先增加与 Agent / RAG / 评测相关的主题段落，避免粘贴无关长文稀释检索信号。

当文档变长后，注意：chunk 数量上升会拉长向量编码时间；金标里的 chunk_id 若仍指向旧语义，需要抽查 get()；简历上的 Recall 数字应在扩库后重跑再写，不要沿用小库饱和指标假装通用。

调试建议：扩库前后各跑一遍检索金标与端到端子集，对比误检索与延迟。若同义改写变好但专有名词变差，检查混合融合是否仍保留词法通路。若延迟明显上升，记录是 embedding、rerank 还是多轮 LLM 占主导。

对面试官可这样表述：语料为可控本地笔记，规模用于验证 Agent 循环与评测体系；方法（混合检索、引用门禁、Workflow 对照）可迁移到更大文献库，但当前数字对应本库配置。

### 评测扩写要点
扩库后至少重跑检索金标与端到端子集。坏例回归集保持可复现。报告写清题数、模型、切分参数与是否含 embedding/rerank。
