# 本地 Embedding 与混合检索（学习笔记）

## Embedding 在检索里做什么

把查询和文档片段映射到同一向量空间，用余弦相似度或内积排序。本地中文场景常用小型句向量模型（如 BAAI/bge-small-zh-v1.5）：首次运行会下载权重，之后离线编码。入库时对每个 chunk 算向量并落盘；查询时只编码 query，再与库存向量比分。

## 词法、向量、混合

词法检索适合专有名词、错误码、公式符号等「必须字面命中」的查询。向量检索适合同义改写与口语化提问。混合检索先两路各取候选，再用 RRF 等法融合：对排名靠前的文档给予更高融合分，不要求两路分数同量纲。

经验上：小而干净的笔记库里，向量或混合的 Recall@k 往往很快饱和；仍应保留词法基线，用来解释「专有名词题」和「同义改写题」上的差异。

## Rerank

Cross-encoder rerank 把「查询 + 候选」拼在一起打分，通常比双塔 embedding 更准，也更慢。做法是：混合召回 top-N，再精排取 top-k。评测要同时报告效果指标与平均延迟；若效果不再提升，延迟数字仍说明工程代价。

## 切分参数

常见起点：chunk_size 约数百字符，overlap 约为其 1/5。过大则噪声多，过小则缺上下文。Overlap 的目的是让跨边界的关键句在相邻 chunk 中至少完整出现一次。改切分后必须重跑 ingest，并检查评测金标里的 chunk_id 是否仍指向正确片段。

## RRF 直觉

若文档在词法榜排名 r1、在向量榜排名 r2，一种简单融合是对每个排名加 1/(k+r) 再求和。k 是平滑常数。这样只依赖名次不依赖原始分，避免「向量分与 BM25 分不可比」的问题。融合后再截断到最终 top-k。

## 何时不要上向量库

语料极小、更新极频、或几乎全是精确字符串匹配时，词法检索可能足够。引入向量要付出：模型下载、编码时间、索引体积与调试复杂度。项目早期可用词法打通 Agent 循环，再在同集金标上补向量与混合，用数字证明收益，而不是先上复杂基础设施。

## 中文分词与词法

中文词法若不做分词，按字符或简单空白切词效果有限。工程上可用正则与字符 n-gram，或接入分词器。无论哪种，评测集应同时包含专有名词题与同义改写题，否则只看平均 Recall 会掩盖短板。

## 向量落盘

编码结果可与 chunk 一并写入索引 JSON，或独立向量文件。最小实现把 embedding 数组和 chunk 放一起，方便单文件 load。注意：换 embedding 模型后旧向量不可混用，必须全量重编码并更新报告里的模型名。

## 近重复文档

笔记库若复制粘贴多段相似说明，检索会返回近重复 chunk，浪费 top-k。去重可按标题、哈希或向量相似度做粗过滤。小库上人工整理往往比上复杂去重管道更划算。


## 补充：实践中的取舍

实习项目的文献库贵在「可复现、可评测、能讲清方法」，不在于堆到百万字。把同一套切分、检索、引用与拒答流程跑通，并保存带配置的评测报告，比盲目扩库更有说服力。扩库时优先增加与 Agent / RAG / 评测相关的主题段落，避免粘贴无关长文稀释检索信号。

当文档变长后，注意：chunk 数量上升会拉长向量编码时间；金标里的 chunk_id 若仍指向旧语义，需要抽查 get()；简历上的 Recall 数字应在扩库后重跑再写，不要沿用小库饱和指标假装通用。

调试建议：扩库前后各跑一遍检索金标与端到端子集，对比误检索与延迟。若同义改写变好但专有名词变差，检查混合融合是否仍保留词法通路。若延迟明显上升，记录是 embedding、rerank 还是多轮 LLM 占主导。

对面试官可这样表述：语料为可控本地笔记，规模用于验证 Agent 循环与评测体系；方法（混合检索、引用门禁、Workflow 对照）可迁移到更大文献库，但当前数字对应本库配置。

### Embedding 扩写要点
全量重编码时间随 chunk 数近似线性增长。换模型必须重编码并更新报告中的模型名。近重复段落增多时，考虑入库前去重或降低过短 chunk。
