# 系统提示、工具 Schema 与 Observation（学习笔记）

## 系统提示的职责

系统提示定义角色、硬规则与输出约束。对文献问答 Agent，通常包括：需要事实时先检索；NO_HITS 后再改写；答案必须带可验证引用；证据不足则拒答；算术走工具；闲聊不检索。把这些写成可检查的条款，比写「请认真回答」更有效。

## 工具描述会进入模型上下文

Function Calling 的 tools 列表（名称、description、parameters JSON Schema）会暴露给模型。description 应说明「何时用 / 何时不用」，例如 search_docs 写明寒暄不要调用。参数 schema 过宽会导致乱传字段；过窄又妨碍合法用法。改工具描述等于改 Agent 行为，需要回归评测。

## Observation 是数据不是新系统指令

工具返回文本会以 tool 消息回灌。若文献片段或网页内容里出现「忽略以上指令」之类句子，应视为不可信数据。系统规则优先级必须高于 Observation。这是文档型提示注入的基本防线。

## 错误 Observation

工具抛错时，把错误摘要当作 Observation 返回，让模型改参数或换策略；不要在 Python 里静默失败后假装成功。同时配合重复调用检测，避免模型对同一坏调用死循环。

## 少即是多

工具集过大时，模型更易选错。文献问答最小集可以是：检索、精读、改写、安全算术。写文件、发邮件、执行任意 shell 不应默认开放。扩展工具前先问：失败时的最大损害是什么。

## 参数校验

即使模型按 schema 调用，仍可能传空字符串或非法类型。工具 run 内应做基本校验，失败返回明确错误 Observation。这比依赖模型「下次改对」更稳。

## 工具结果截断

Observation 过长会挤占后续推理上下文。检索结果可先返回短列表，详情交给 read_chunk。截断时保留 chunk_id，避免模型引用看不到的正文。


## 补充：实践中的取舍

实习项目的文献库贵在「可复现、可评测、能讲清方法」，不在于堆到百万字。把同一套切分、检索、引用与拒答流程跑通，并保存带配置的评测报告，比盲目扩库更有说服力。扩库时优先增加与 Agent / RAG / 评测相关的主题段落，避免粘贴无关长文稀释检索信号。

当文档变长后，注意：chunk 数量上升会拉长向量编码时间；金标里的 chunk_id 若仍指向旧语义，需要抽查 get()；简历上的 Recall 数字应在扩库后重跑再写，不要沿用小库饱和指标假装通用。

调试建议：扩库前后各跑一遍检索金标与端到端子集，对比误检索与延迟。若同义改写变好但专有名词变差，检查混合融合是否仍保留词法通路。若延迟明显上升，记录是 embedding、rerank 还是多轮 LLM 占主导。

对面试官可这样表述：语料为可控本地笔记，规模用于验证 Agent 循环与评测体系；方法（混合检索、引用门禁、Workflow 对照）可迁移到更大文献库，但当前数字对应本库配置。

### 提示与工具扩写要点
工具 description 随场景迭代：库变大后更要写清「何时不调用」。Observation 截断策略要保留 chunk_id。错误回传仍然必要。
