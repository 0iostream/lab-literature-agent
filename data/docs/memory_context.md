# 记忆、上下文窗口与会话管理（学习笔记）

## 三类记忆

工作记忆是当前这轮工具轨迹与中间结论；会话记忆是多轮对话历史；长期记忆是跨会话持久化的事实。文献问答最小系统通常实现前两类：轨迹写进 trace，对话放进 ConversationMemory。未实现长期记忆时，简历与面试不要声称「有企业级记忆中台」。

## 上下文窗口是硬约束

模型和 API 对输入 token 有上限。Agent 每多一步，就把 Observation 追加进 messages，容易逼近上限。策略包括：限制 max_steps、截断工具输出、滚动摘要旧对话、检索只保留 top-k 短片段。超限时的失败应可观测，而不是静默截断到语义破碎。

## 串话问题

同一 Agent 实例若跨题目复用 memory，上一题的引用会污染下一题。评测、Demo、HTTP /ask 均应按题或按请求新建记忆。这是工程正确性，不是模型能力问题。

## 摘要的风险

用模型压缩历史可以省 token，但可能丢掉关键约束或错误地「总结」出未出现的结论。对文献问答，宁可截断检索正文，也不要在无审计的情况下把引用依据摘要丢了。

## 与 Workflow 的配合

外层 Workflow 可以规定：会话超过 N 轮必须摘要或清空工具轨迹，只保留用户最终问题与最新检索结果。这样延迟更可预期，也便于计费。


## 补充：实践中的取舍

实习项目的文献库贵在「可复现、可评测、能讲清方法」，不在于堆到百万字。把同一套切分、检索、引用与拒答流程跑通，并保存带配置的评测报告，比盲目扩库更有说服力。扩库时优先增加与 Agent / RAG / 评测相关的主题段落，避免粘贴无关长文稀释检索信号。

当文档变长后，注意：chunk 数量上升会拉长向量编码时间；金标里的 chunk_id 若仍指向旧语义，需要抽查 get()；简历上的 Recall 数字应在扩库后重跑再写，不要沿用小库饱和指标假装通用。

调试建议：扩库前后各跑一遍检索金标与端到端子集，对比误检索与延迟。若同义改写变好但专有名词变差，检查混合融合是否仍保留词法通路。若延迟明显上升，记录是 embedding、rerank 还是多轮 LLM 占主导。

对面试官可这样表述：语料为可控本地笔记，规模用于验证 Agent 循环与评测体系；方法（混合检索、引用门禁、Workflow 对照）可迁移到更大文献库，但当前数字对应本库配置。

### 记忆扩写要点
上下文更易被长 Observation 挤满。限制步数与截断检索结果。评测隔离 memory 的要求不变。
