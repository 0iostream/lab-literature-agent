# 切分、入库与索引运维（学习笔记）

## 切分参数

chunk_size 控制片段长度，overlap 控制相邻片段共享前缀。本仓库默认按字符切分：简单、可复现，但对中英文混合与 Markdown 标题不感知。改进方向包括按标题边界优先切、再对过长节二次切，但改策略后必须重跑金标抽查。

## ingest 流程

读取 docs 目录 -> 切分 -> 分配 doc_id#index -> 可选 embedding -> 写 chunks.json。失败应整次可见，避免「半份索引」。Windows 上注意路径与编码为 UTF-8。

## 版本与可复现

简历与评测报告应能对应到某次索引状态：文档列表、切分参数、embedding 模型名。若只改了文档却未重 ingest，线上 Agent 仍读旧索引，会造成「我明明改了笔记为什么还答旧内容」。

## 空文档与噪声

空文件、纯目录说明、重复粘贴的许可证全文会污染检索。入库前可过滤过短片段。教学库保持主题相关，比盲目堆文件更能提高评测可读性。

## 与精读工具的关系

search_docs 返回若干短片段后，read_chunk 按 id 取全文（该 chunk 的完整文本）。切分过碎时，精读帮助有限；切分过粗时，精读等于把噪声整段塞回模型。参数要和工具设计一起调。


## 补充：实践中的取舍

实习项目的文献库贵在「可复现、可评测、能讲清方法」，不在于堆到百万字。把同一套切分、检索、引用与拒答流程跑通，并保存带配置的评测报告，比盲目扩库更有说服力。扩库时优先增加与 Agent / RAG / 评测相关的主题段落，避免粘贴无关长文稀释检索信号。

当文档变长后，注意：chunk 数量上升会拉长向量编码时间；金标里的 chunk_id 若仍指向旧语义，需要抽查 get()；简历上的 Recall 数字应在扩库后重跑再写，不要沿用小库饱和指标假装通用。

调试建议：扩库前后各跑一遍检索金标与端到端子集，对比误检索与延迟。若同义改写变好但专有名词变差，检查混合融合是否仍保留词法通路。若延迟明显上升，记录是 embedding、rerank 还是多轮 LLM 占主导。

对面试官可这样表述：语料为可控本地笔记，规模用于验证 Agent 循环与评测体系；方法（混合检索、引用门禁、Workflow 对照）可迁移到更大文献库，但当前数字对应本库配置。

### 切分运维扩写要点
文档增长后重新评估 chunk_size/overlap。ingest 失败要可见。索引版本与评测报告对齐。
