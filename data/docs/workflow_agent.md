# Workflow、Agent 与 MCP

## 怎么区分

- Tool：一次有明确输入输出的能力，例如 search_docs。
- Workflow：步骤由代码写死，例如「先检索再生成再校验引用」。延迟和分支可预期。
- Agent：下一步由模型选择。适合分支事先说不清的任务。

落地常用混合：外层 Workflow 保证超时、权限和日志，内层个别节点交给 Agent。不要为了多 Agent 而多 Agent。

## 记忆分层

- 工作记忆：当前这一轮的工具轨迹。
- 会话记忆：最近对话，太长就做滚动摘要。
- 长期记忆：跨会话的事实。写入时区分「用户陈述的事实」和「模型自己的推断」。

## 协议

- MCP（Model Context Protocol）：Agent 与工具之间的标准接口，属于垂直方向。
- A2A：Agent 与 Agent 之间的通信，属于水平方向。
- Skills：可复用的能力说明，不是传输协议。

把聊天机器人加上按关键词触发的插件，并不等于 Agent。关键看有没有「行动-观察」闭环和多步自主决策。

## 何时用固定 Workflow

问题类型稳定、步骤可穷举时，用固定链更稳、更便宜、也好评测。典型文献问答：检索 → 生成 → 校验引用；校验失败可有限重试，仍失败则拒答。算术与闲聊若也强行进「必检索」Workflow，会引入误检索，这时更适合 Agent 或前置路由。

## 对比实验怎么写

比较 Workflow 与 Agent 时，应固定同一批问题、同一检索后端与同一生成模型，报告成功率、平均步数、延迟、token（真实或标明估算）和错误类型，而不是只比框架名词。小语料上两边成功率都可能打满，此时延迟与步数更能说明取舍。

## LangGraph 一类框架的定位

图状态机把节点写成「读 state、返回局部更新」，边与条件边由代码决定下一跳。适合表达固定三节点：search → generate → check_citation。它不自动等于更好的 Agent；若节点内部仍让模型自由选工具，那只是把 Agent 嵌进了 Workflow。选择框架前先画清：哪些边必须写死。

## HITL 与副作用

删除、发送、付款等工具需要权限与人工确认（HITL）。文献问答默认只读，降低误操作面。若将来加「写入笔记库」类工具，应单独鉴权，并在 Workflow 外层做审计日志，而不是交给模型自由连点。

## 会话隔离

评测与 HTTP 服务都应按请求或按题目新建会话记忆，避免上一题的引用与结论污染下一题。Demo 连续跑多题时尤其容易忽略这一点，表现为「第二题没搜却答出了第一题的文献」。

## 路由层

生产系统可在最外层加一个轻量路由器：闲聊直出、算术走计算器、文献题进 RAG/Agent。路由可以是规则、小分类模型或一次短提示，但应可测。没有路由时，固定「必检索」Workflow 会在闲聊题上表现差，这不是生成模型单独的问题。

## 可观测性字段

一次请求建议记录：request_id / trace_id、选用的流水线（Workflow 或 Agent）、步数、工具列表、延迟、停止原因、是否拒答。便于对比版本与定位「变慢」是检索、rerank 还是多轮 LLM。


## 补充：实践中的取舍

实习项目的文献库贵在「可复现、可评测、能讲清方法」，不在于堆到百万字。把同一套切分、检索、引用与拒答流程跑通，并保存带配置的评测报告，比盲目扩库更有说服力。扩库时优先增加与 Agent / RAG / 评测相关的主题段落，避免粘贴无关长文稀释检索信号。

当文档变长后，注意：chunk 数量上升会拉长向量编码时间；金标里的 chunk_id 若仍指向旧语义，需要抽查 get()；简历上的 Recall 数字应在扩库后重跑再写，不要沿用小库饱和指标假装通用。

调试建议：扩库前后各跑一遍检索金标与端到端子集，对比误检索与延迟。若同义改写变好但专有名词变差，检查混合融合是否仍保留词法通路。若延迟明显上升，记录是 embedding、rerank 还是多轮 LLM 占主导。

对面试官可这样表述：语料为可控本地笔记，规模用于验证 Agent 循环与评测体系；方法（混合检索、引用门禁、Workflow 对照）可迁移到更大文献库，但当前数字对应本库配置。

### Workflow 扩写要点
语料变长后，固定 Workflow 仍适合「必检索」通道；但路由（闲聊/算术/文献）更重要。对比实验保持同题同模型，报告步数与延迟，避免只报成功率。
