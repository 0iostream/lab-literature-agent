# 混合检索与 RRF 细节（学习笔记）

## 为什么要混合

词法强在字面：专有名词、错误码、论文年份。向量强在同义：口语化、换说法。单一通道会在某一类题上系统性偏弱。混合的目标不是「永远更高」，而是在同一金标上同时照顾两类查询。

## RRF 公式直觉

对每个候选文档，把它在各路排序中的名次 r 换成 1/(k+r) 再相加。k 常用较小常数，避免第一名过度独占。只依赖名次，因此不必把 BM25 分数与余弦相似度强行校准到同一量纲。

## 与加权分数融合的差别

也可以把两路分数 min-max 后加权求和，但权重敏感、分数分布一变就要重调。RRF 更钝、更好作为默认融合。若某路召回极差，RRF 也无法凭空造出相关文档，仍需先保证单路质量。

## 评测怎么讲故事

报告应同时给出 lexical / vector / hybrid 的 Recall@k 与 MRR，并举例：专有名词题上词法不差、同义改写题上向量更好。小库打满时，如实写「指标饱和」，把价值放在方法可复现与延迟对比，而不是夸大绝对分数。

## 接 rerank 的位置

通常在混合融合后的 top-N 上跑 cross-encoder，再取 top-k 给生成或 Agent。N 太小，rerank 无空间；N 太大，延迟线性变差。延迟数字必须实测，不要照抄博客。


## 补充：实践中的取舍

实习项目的文献库贵在「可复现、可评测、能讲清方法」，不在于堆到百万字。把同一套切分、检索、引用与拒答流程跑通，并保存带配置的评测报告，比盲目扩库更有说服力。扩库时优先增加与 Agent / RAG / 评测相关的主题段落，避免粘贴无关长文稀释检索信号。

当文档变长后，注意：chunk 数量上升会拉长向量编码时间；金标里的 chunk_id 若仍指向旧语义，需要抽查 get()；简历上的 Recall 数字应在扩库后重跑再写，不要沿用小库饱和指标假装通用。

调试建议：扩库前后各跑一遍检索金标与端到端子集，对比误检索与延迟。若同义改写变好但专有名词变差，检查混合融合是否仍保留词法通路。若延迟明显上升，记录是 embedding、rerank 还是多轮 LLM 占主导。

对面试官可这样表述：语料为可控本地笔记，规模用于验证 Agent 循环与评测体系；方法（混合检索、引用门禁、Workflow 对照）可迁移到更大文献库，但当前数字对应本库配置。

### RRF 扩写要点
候选池变大时，先融合再截断，再视需要 rerank。记录 N 与 k。小库饱和时诚实说明，把故事放在方法与延迟。
