# LLM API、超时重试与本地运行（学习笔记）

## OpenAI 兼容接口

许多国内模型提供与 OpenAI Chat Completions 兼容的 HTTP API：同一套 messages、tools、temperature 字段，只需改 base_url、api_key、model。客户端应把密钥放在环境变量或 .env，禁止提交到仓库。

## 超时与重试

网络抖动、限流（429）与部分 5xx 适合有限次重试，并加指数退避。参数错误、鉴权失败不应盲重试。重试耗尽后向上抛出受控错误，由 Agent 或 API 层映射为明确失败，而不是空字符串假装成功。

## Temperature 与评测稳定性

对照实验与端到端评测常用较低 temperature，降低随机性。演示聊天可以略高。报告中应写明模型名与关键采样参数，否则别人无法复现你的成功率数字。

## 本地 Embedding 与云端生成

常见混合架构：生成走云端 Chat API，检索向量用本地 sentence-transformers。这样检索不消耗生成额度，也便于离线重建索引。首次下载模型需网络；之后应能离线 encode。

## 服务化注意点

把 Agent 暴露为 HTTP 时：/health 不跑完整推理；/ask 限制问题长度、整题超时、区分校验错误与上游模型错误。并发下注意每请求独立 memory，以及本地 embedding 模型的线程/进程安全策略。

## 空响应与残缺 tool_call

偶发空 choices、或 tool_call 缺参数，应视为可重试或可降级错误。客户端检测到后不要把 None 当正常字符串继续拼 messages。API 层可映射为 502，并带 request_id 方便查日志。

## 配置集中管理

模型名、超时、最大步数、问题长度上限等放配置与环境变量，避免散落魔法数。改配置后跑一小撮回归题，确认不是「默默换模型」导致指标跳动。


## 补充：实践中的取舍

实习项目的文献库贵在「可复现、可评测、能讲清方法」，不在于堆到百万字。把同一套切分、检索、引用与拒答流程跑通，并保存带配置的评测报告，比盲目扩库更有说服力。扩库时优先增加与 Agent / RAG / 评测相关的主题段落，避免粘贴无关长文稀释检索信号。

当文档变长后，注意：chunk 数量上升会拉长向量编码时间；金标里的 chunk_id 若仍指向旧语义，需要抽查 get()；简历上的 Recall 数字应在扩库后重跑再写，不要沿用小库饱和指标假装通用。

调试建议：扩库前后各跑一遍检索金标与端到端子集，对比误检索与延迟。若同义改写变好但专有名词变差，检查混合融合是否仍保留词法通路。若延迟明显上升，记录是 embedding、rerank 还是多轮 LLM 占主导。

对面试官可这样表述：语料为可控本地笔记，规模用于验证 Agent 循环与评测体系；方法（混合检索、引用门禁、Workflow 对照）可迁移到更大文献库，但当前数字对应本库配置。

### API 运维扩写要点
超时、重试与空响应处理不随语料增大而改变优先级。配置集中管理；改模型后跑回归。
