# ReAct：Reasoning and Acting

ReAct 把推理（Reasoning）和行动（Acting）交错进行。论文：Yao et al., 2022。

## 三个字母

- Reasoning（Thought）：模型用自然语言写下当前判断。
- Acting（Action）：选择一个工具并给出参数。
- Observation：环境或工具返回的结果，进入下一步 Thought。

循环直到模型给出最终答案，或达到步数上限。

## 解决什么问题

纯 Chain-of-Thought 不能获取新信息，也改不了外部状态。纯工具调用缺少中间推理，容易选错工具。ReAct 用 Observation 纠正 Thought，减少幻觉，并让轨迹可检查。

## 工程上必做的三件事

1. 最大步数，防止死循环。
2. 检测重复的工具调用，逼模型停下来。
3. 工具失败时把错误当 Observation 回传，而不是在代码里静默吞掉。

## 和 Function Calling 的关系

现代实现里，「Action」常表现为模型返回的 tool_call（工具名 + JSON 参数），而不是手写字符串解析。Observation 则是本地执行工具后的返回文本，再以 tool 角色消息回灌。Prompt 仍可要求模型在调用前写出简短 Thought，便于排错与评测。

## 停止条件与收尾

除了模型主动给出最终答案，常见停止原因还包括：达到 max_steps、触发重复调用熔断、引用门禁失败且重试耗尽、用户输入被安全规则拦截。收尾时应写清 stopped_reason，方便对比不同策略，而不是只打印最后一段自然语言。

## 轨迹（Trace）要记什么

一条可排错的轨迹至少包含：trace_id、每一步的工具名与参数摘要、Observation 是否失败、耗时、停止原因。Token 若只能粗估，要在报告里标明「估算」，不要伪装成计费 API 返回值。失败轨迹同样有价值：可用来归纳 bad case 和回归测试。

## 常见失败模式

- 该检索却直接回答：缺少强制「需要事实先 search」的系统规则。
- 检索无命中仍编造引用：必须做 chunk_id 存在性校验，并允许明确拒答。
- 同一错误工具调用连打多次：需要重复调用检测。
- 算术用心算：应强制走计算器类工具，避免数字幻觉。

## 系统提示怎么约束 ReAct

系统提示应写清：何时必须检索、NO_HITS 后何时改写、最终答案的引用格式、证据不足如何拒答、算术与闲聊分别怎么处理。规则过少会导致模型走捷径；规则过多又会挤占上下文。实践上优先写「可验证」的硬约束（必须引用真实 chunk_id），把风格类要求放短。

## 多跳问题

多跳指：第一步检索的结果决定第二步该搜什么。例如先确认某个术语定义，再根据定义去查工程约束。固定 Workflow 很难穷举所有跳转；ReAct 更合适，但仍需 max_steps，否则模型可能无意义地反复搜索。评测多跳题时，相关 chunk 可能不止一个，Recall@k 应用集合命中来算。

## 与「伪 Agent」的区别

仅按关键词路由到插件、或固定「永远先搜再答」的流水线，都不是完整 ReAct。ReAct 的关键是：每一步的工具选择依赖上一轮 Observation，并且存在可检查的 Thought-Action-Observation 轨迹。面试时可用自己仓库里的 trace 文件对照说明。

## 调试 Checklist

当 Agent 行为异常时，按顺序查：系统提示是否被改坏；tools schema 是否仍描述清楚；最近几条 Observation 是否含 ERROR；是否触发重复调用；引用门禁是否误杀合法拒答；trace 里 stopped_reason 是什么。多数问题能在这六步内定位，无需先换模型。

## 评测集设计提示

端到端题应覆盖：必检索事实题、同义改写、多要点、应拒答、算术、闲聊。每类至少几道，避免「全是事实题」导致工具选择准确率虚高。金标里标注 should_search / should_refuse / expect_tools，评测脚本按标注自动判分。


## 补充：实践中的取舍

实习项目的文献库贵在「可复现、可评测、能讲清方法」，不在于堆到百万字。把同一套切分、检索、引用与拒答流程跑通，并保存带配置的评测报告，比盲目扩库更有说服力。扩库时优先增加与 Agent / RAG / 评测相关的主题段落，避免粘贴无关长文稀释检索信号。

当文档变长后，注意：chunk 数量上升会拉长向量编码时间；金标里的 chunk_id 若仍指向旧语义，需要抽查 get()；简历上的 Recall 数字应在扩库后重跑再写，不要沿用小库饱和指标假装通用。

调试建议：扩库前后各跑一遍检索金标与端到端子集，对比误检索与延迟。若同义改写变好但专有名词变差，检查混合融合是否仍保留词法通路。若延迟明显上升，记录是 embedding、rerank 还是多轮 LLM 占主导。

对面试官可这样表述：语料为可控本地笔记，规模用于验证 Agent 循环与评测体系；方法（混合检索、引用门禁、Workflow 对照）可迁移到更大文献库，但当前数字对应本库配置。

### ReAct 扩写要点
在更长语料上，模型更容易检索到「看起来相关但非直接答案」的片段。系统提示应强调：最终论断必须能被引用片段支持；多跳时先确认中间实体再搜下一步。步数上限可随任务难度略增，但要在评测里报告平均步数，防止无界探索。
